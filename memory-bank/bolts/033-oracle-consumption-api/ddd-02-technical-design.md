# Technical Design - Oracle Consumption API

## Architecture Pattern

Lógica de consumo no Oracle, em PL/SQL. O indicador e o texto nascem no banco, não numa conta feita no Java.

Este bolt entrega só scripts SQL versionados. Não altera o `admin-api`, o `JdbcTemplate` do Postgres nem o Prisma. O segundo datasource e o JDBC ficam no bolt 034.

Os objetos nascem no schema do usuário Oracle conectado. Nenhum script grava URL, usuário ou senha. A conexão fica fora do Git, por ambiente (`ORACLE_URL`, `ORACLE_USERNAME`, `ORACLE_PASSWORD`), para o operador aplicar os scripts e para o Java usar depois.

Compatibilidade alvo: Oracle 12c ou mais recente, com `IDENTITY` e character set Unicode (`AL32UTF8`). Os scripts são idempotentes no estilo 19c: bloco anônimo consulta o dicionário antes de criar tabela, e as functions usam `CREATE OR REPLACE`.

## Layer Structure

```text
┌─────────────────────────────┐
│      Presentation           │  Cliente SQL local (SQLcl ou SQL*Plus). Sem HTTP neste bolt.
├─────────────────────────────┤
│      Application            │  Ordem dos scripts: DDL, seed, functions.
├─────────────────────────────┤
│        Domain               │  FN_INDICADOR_TOKENS e FN_CONSUMO_FORMATADO
├─────────────────────────────┤
│     Infrastructure          │  Tabelas USUARIO_CONSUMO, LEITURA_CONSUMO, ALERTA_CONSUMO
└─────────────────────────────┘
```

`apps/admin-api/src/main/resources/db/oracle/`

| Arquivo | Papel |
|---------|--------|

## API Design

Não há endpoint HTTP neste bolt. O contrato é a assinatura SQL, chamada a partir de `DUAL`.

| Contrato | Chamada | Entrada | Saída |
|----------|---------|---------|-------|
| `FN_INDICADOR_TOKENS` | `SELECT FN_INDICADOR_TOKENS(:id, :inicio, :fim) FROM DUAL` | `p_usuario_id NUMBER`, `p_inicio TIMESTAMP`, `p_fim TIMESTAMP` | `NUMBER` — soma dos tokens |
| `FN_CONSUMO_FORMATADO` | `SELECT FN_CONSUMO_FORMATADO(:id, :inicio, :fim) FROM DUAL` | os mesmos três parâmetros | `VARCHAR2(400)` — uma frase |

O parâmetro de usuário é a chave primária numérica (`USUARIO_CONSUMO.ID`). O identificador externo serve ao seed e à prova de que o dado é fictício. Não entra na function.

`FN_CONSUMO_FORMATADO` chama `FN_INDICADOR_TOKENS`. O limite 10.000 fica em comentário no corpo e numa constante local `c_limite NUMBER := 10000`.

Frase estável, para o teste bater caractere a caractere:

- alto: `{nome} consumiu {total} tokens no período. Consumo alto.`
- normal: `{nome} consumiu {total} tokens no período. Consumo normal.`

`{total}` é o número inteiro sem separador de milhar. O nome sai da coluna `NOME`, com acento.

## Data Persistence

| Tabela | Colunas | Relacionamentos |
|--------|---------|-----------------|
| `USUARIO_CONSUMO` | `ID NUMBER GENERATED BY DEFAULT AS IDENTITY` PK; `NOME VARCHAR2(120 CHAR)` NOT NULL; `IDENTIFICADOR_EXTERNO VARCHAR2(64 CHAR)` NOT NULL | UK em `IDENTIFICADOR_EXTERNO` |
| `LEITURA_CONSUMO` | `ID NUMBER GENERATED BY DEFAULT AS IDENTITY` PK; `USUARIO_ID NUMBER` NOT NULL; `QUANTIDADE_TOKENS NUMBER(12)` NOT NULL; `INSTANTE TIMESTAMP` NOT NULL | FK `USUARIO_ID` → `USUARIO_CONSUMO(ID)` sem `ON DELETE CASCADE`. Check `QUANTIDADE_TOKENS >= 0`. Índice `(USUARIO_ID, INSTANTE)` |
| `ALERTA_CONSUMO` | `ID` identity PK; `USUARIO_ID NUMBER` NOT NULL; `INICIO TIMESTAMP` NOT NULL; `FIM TIMESTAMP` NOT NULL; `TOTAL_TOKENS NUMBER(12)` NOT NULL; `MENSAGEM VARCHAR2(400 CHAR)` NOT NULL; `CRIADO_EM TIMESTAMP DEFAULT SYSTIMESTAMP` NOT NULL | FK para `USUARIO_CONSUMO(ID)` sem cascade. Check `TOTAL_TOKENS >= 0` e `INICIO <= FIM`. UK `(USUARIO_ID, INICIO, FIM)` já reserva a regra de não duplicar alerta. Este bolt não insere linha |

DDL idempotente: se `USER_TABLES` já tem a tabela, o bloco não executa o `CREATE`. O mesmo vale para índice e constraints consultando `USER_INDEXES` e `USER_CONSTRAINTS`. Reexecutar não quebra a PK.

### Seed

Período de demonstração, intervalo fechado:

`TIMESTAMP '2026-09-01 00:00:00'` até `TIMESTAMP '2026-09-30 23:59:59'`

| Identificador externo | Nome | Leituras | Total no período |
|-----------------------|------|----------|------------------|
| `sim-abaixo-limite` | Ana Clara | 2026-08-31 23:59:59 = 9000 (fora); 2026-09-01 00:00:00 = 1500 (entra); 2026-09-15 12:00:00 = 2000 (entra) | 3500 |
| `sim-no-limite` | Bruno Alves | 2026-09-01 00:00:00 = 4000 (entra); 2026-09-30 23:59:59 = 6000 (entra); 2026-10-01 00:00:00 = 5000 (fora) | 10000 |
| `sim-sem-leitura` | Clara Sem Leituras | nenhuma | 0 |

Usuários entram por `MERGE` em `IDENTIFICADOR_EXTERNO`. Leituras entram só com `INSERT ... SELECT ... WHERE NOT EXISTS` na combinação usuário + instante + quantidade. Segunda execução não duplica a série.

Nenhum identificador imita uid do Supabase ou do Firebase.

### Resultados esperados no período de demonstração

| Chamada | Resultado |
|---------|-----------|
| Indicador de Ana Clara | `3500` |
| Indicador de Bruno Alves | `10000` |
| Indicador de Clara Sem Leituras | `0` |
| Texto de Ana Clara | `Ana Clara consumiu 3500 tokens no período. Consumo normal.` |
| Texto de Bruno Alves | `Bruno Alves consumiu 10000 tokens no período. Consumo alto.` |
| Texto de Clara | `Clara Sem Leituras consumiu 0 tokens no período. Consumo normal.` |
| `p_usuario_id = 999999` | erro `-20001`, sem retorno numérico |
| início `2026-09-30 23:59:59` e fim `2026-09-01 00:00:00` | erro `-20002`, sem retorno numérico |

Os ids numéricos saem do `MERGE ... RETURNING` ou de um `SELECT` pelo identificador externo. O teste não depende de um `ID` fixo.

## Security Design

| Concern | Approach |
|---------|----------|
| Authentication | Sem HTTP. Quem aplica o script já está conectado no Oracle local. Credenciais não entram no arquivo. |
| Authorization | O usuário Oracle precisa de `CREATE TABLE` e `CREATE PROCEDURE`. Os objetos ficam no schema dele. Sem `GRANT` para outro schema neste bolt. |
| Data Encryption | Série simulada, sem dado real. Segredo do banco só em variável de ambiente, fora do Git. |
| Isolamento | Scripts não referenciam Postgres, Prisma nem Supabase. Falha de conexão Oracle não altera o outro banco. |

## NFR Implementation

| Requirement | Design Approach |
|-------------|-----------------|
| Performance | Índice `(USUARIO_ID, INSTANTE)` e um `SUM` por chamada. O seed tem dez linhas no máximo. A meta de tela abaixo de 3 s pertence ao bolt da API. |
| Scalability | Volume de demonstração. Sem partição, fila ou cache. |
| Reliability | Function não devolve 0 quando o usuário não existe nem quando o período é inválido. Seed e DDL podem rodar de novo. Oracle desligado: o cliente SQL falha na conexão e o Postgres permanece como está. |
| Comentários | Cada function abre com comentário de propósito. `FN_CONSUMO_FORMATADO` documenta o limite 10.000 no comentário. |

## Error Handling

Ordem interna das functions: período inválido, depois existência do usuário, depois a soma. `NULL` em início, fim ou id conta como período inválido no caso das datas e como usuário inexistente no caso do id.

| Error Type | Code | Response |
|------------|------|----------|
| Usuário inexistente | `-20001` | `RAISE_APPLICATION_ERROR(-20001, 'Usuário de consumo inexistente.')` dentro do `EXCEPTION`. Não retorna 0. |
| Período inválido | `-20002` | `RAISE_APPLICATION_ERROR(-20002, 'Período inválido: início posterior ao fim.')` dentro do `EXCEPTION`. Não retorna 0. |
| Outras falhas SQL | re-raise | `WHEN OTHERS THEN RAISE;` para não engolir erro de tabela ausente. |
| Usuário existente sem leitura | nenhum | `NVL(SUM(...), 0)` devolve 0. |

`FN_CONSUMO_FORMATADO` não captura `-20001` nem `-20002` para transformar em frase. A exceção de `FN_INDICADOR_TOKENS` sobe. O `EXCEPTION` da function de texto só faz `WHEN OTHERS THEN RAISE`.
